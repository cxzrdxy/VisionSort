## 一、这套程序是什么

小零件（样例为齿轮类）的人工分拣效率低、漏检不可追溯。VisionSort 是这条线的**上位机软件**：传送带把零件送进相机视野，光电传感器硬触发相机取像，VisionPro 用 PatMax 模板定位并判定合格与否，不合格件由四轴机械臂实时抓走，全过程数据落库可追溯。

一句话概括全链路：

```
光电触发 ─→ GigE 取像 ─→ PatMax 定位/判定 ─→ 九点标定换算成机械臂 mm
                                                      │
   落库(MySQL) ←─ 存图(OK/NG) ←─ 记录 ←───────────────┴──→ NG 抓取放废料区
```

界面是 5 个功能页的单窗口 Tab 程序：**主运行 / 设备调试 / 视觉配置 / 数据日志 / 系统设置**。


| 工程 | 输出 | 位数 | 为什么是这个位数 |
|---|---|---|---|
| **VisionSort** | `VisionSort.exe`（WinForms 主程序） | **x64** | VisionPro 9.0 是 x64 混合模式程序集，宿主必须 64 位 |
| **DobotArm** | 类库（被主程序引用） | AnyCPU | 不碰原生 DLL，只经回环 UDP 指挥桥接进程；可独立编译与测试 |

## 四、构建与运行

1. 双击 `VisionSort.sln` 打开。
2. **平台选 `x64`**（解决方案配置里 Debug|x64 或 Release|x64）。
   - `DobotArmBridge` 在解决方案里已把任意平台映射到 `x86`；它自己还有一道构建期硬门槛 `EnsureX86`：`PlatformTarget != x86` 直接编译失败，防止被 ProjectReference 传进来的 x64 静默带错。
3. 生成 → 生成解决方案。输出在 `VisionSort\bin\x64\<Configuration>\net48\`。
   - 构建后会自动把桥接进程及其 6 个原生 DLL 拷到输出的 `ArmBridge\` 子目录（`CopyArmBridge` 目标：必须写成 Target 而不是 ItemGroup，否则项目评估 glob 时桥接还没构建过，会**静默漏拷**）。
   - `九点标定操作指引.md` 作为嵌入资源编进 exe，供界面「操作指引」按钮显示。**改了那份 .md 必须重新编译**才会生效——这是刻意的：让程序里的说明与文档永远同一份。
4. 直接运行 `VisionSort.exe`。默认会自动拉起 `ArmBridge\DobotArmBridge.exe`；要单独观察桥接进程的控制台与日志，可在系统设置页取消「自动启动桥接进程」后手动运行它（日志写在同目录 `DobotArmBridge.log`）。

**编译期已知坑（不要"顺手改回去"）：** `App.config` 里**不要**加 `System.Windows.Forms.ApplicationConfigurationSection`（含 DpiAwareness）。它是 .NET Framework 4.7+ 的内置节，用户声明会让**整个配置系统**初始化失败，进而让 `MySqlConnector` 每次 `Open()` 都失败——打包出去的程序连不上 MySQL。完整实测过程见 [数据库方案.md](数据库方案.md) §二十。

## 五、首次部署顺序

按这个顺序走，每一步都能单独验证，出错时不用怀疑上游：

1. **系统设置页**——四组参数（Modbus 传送带 / 生产视觉参数 / 机械臂连接与延时 / MySQL 连接）逐项校验后点「保存参数」，落到 `config\sysparam.json`。
   - 注意分组：**抓取几何**（抓取高度 Z、工作范围、待机/放料点）不在这里，它们与九点标定一起存 `config\calib.json`，入口在设备调试页的标定区。
2. **系统设置页 → 「初始化建表」**——在目标库里建 `vision_result` 表。不建表程序仍能跑，但结果会先落到本机补写文件（`config\pending_results.jsonl`）而进不了库。
3. **视觉配置页**——连接相机（枚举 → 视频格式 → 曝光/增益 → 建 FIFO）→ 加载或另存 VPP 方案（默认目录 `<exe>\vpps\`）→ 训练 PMA 模板（训练图、区域、搜索范围、阈值，训练后做原点核对与自检）。
4. **设备调试页**——连接传送带（正反转/停止/调速试动）→ 连接机械臂（点动、读位姿、吸盘）→ **做九点标定**（读机械臂位姿回填、拟合、看 RMSE/精度/旋转/手性四项指标）→ 点「保存」，写 `config\calib.json`。
   - 标定是"不报错的错误"的重灾区：模板原点没设、变换方向取反、X/Y 配成镜像，程序都判定正常但抓取必偏。详见 [九点标定联机分拣方案.md](九点标定联机分拣方案.md)。
5. **主运行页**——先「单次运行」试跑一轮（看状态链、OK/NG 灯、统计与存图），确认无误再「连续运行」。

## 六、现场接线与通信参数

| 设备 | 物理接口 | 参数 | 默认值 | 配置入口 |
|---|---|---|---|---|
| GigE 相机 | 网口（GigE Vision） | 由 VisionPro 采集层管理 | 曝光/增益/包大小/延迟级别/触发模式在视觉配置页设 | 视觉配置页 |
| 机械臂 | USB 串口 | 115200-8-N-1 | 串口 `COM3`（可填 `auto` 让官方 DLL 自己搜）；回环 UDP `127.0.0.1:18899` | 系统设置页 → 机械臂配置 |
| 传送带变频器 | 串口（RTU） | 9600-8-N-1，站号 **2** | `COM5`；**100=启停（1 启动 / 0 停止）**、**101=方向（0 反转 / 1 正转）**、**102=速度（ushort 直写）** | 系统设置页 → 传送带配置 |
| MySQL | TCP | 127.0.0.1:3306 | 库 `vision_sort`、表 `vision_result`、用户 `vision`；`ConnectionTimeout=3` | 系统设置页 → 数据库配置 |

> 寄存器语义以现场示例工程（`day30\03-code\MyModBus\...\BeltControl.cs`）为准，2026-09-18 更正过一版：早先"100=正转启停、101=反转启停、正反转互锁"的记录**是错的**。故障复位暂定＝停止（写 100=0），现场若有专用复位寄存器，改 `ConveyorSettings.ResetAsync` 一处。
>
> 机械臂与 VisionPro 的位数冲突靠**回环 UDP 自研 KV 协议**打通：`cmd=moveJ;seq=7;x=200.0;y=30.0;z=-50.0;r=0`（单行 key=value、UTF-8、值内 `;`/CR/LF 转义，共 12 条命令）。选 KV 而不是 JSON 的理由是零依赖、零转义坑、人能读能手打——现场可以用 PowerShell 直接发一行报文验证桥接进程，不必启动 VisionSort。

## 十、注意事项（运维与二次开发必读）

这些都是**踩过并已用代码兜住**的坑，改动相关代码前先读一遍：

1. **位数**：主程序必须 x64，桥接进程必须 x86。不要试图把原生 DLL 引进主程序，也不要为了"省一个进程"把桥接合进来。
2. **一台 GigE 相机同时只能被一个 FIFO 打开**——相机页与主运行页原先各持一个 FIFO，会互抢（现场表现为"连不上/取不到图"，极难排查）。现已抽成共享单例 `CameraService`，两个页面共用一个 FIFO；新增取像入口也必须走它。
3. **NModbus 主站非线程安全**：界面 500ms 轮询 + 按钮动作 + 生产循环并发进入会**串包**（表现为"刚点正转但回读还是停止"）。所有主站访问都必须过 `ConveyorSettings` 里的信号量闸。
4. **`CogPMAlignTool.RunParams.AcceptThreshold` 会把结果从 `Results` 集合里直接滤掉**（不是标记 `Accepted=false`）。同一张 0.9401 的图，阈值 0.90 时 `Results.Count` 直接变 0 → 判 NG 时拿不到像素坐标 → **分拣永远不动作且不报错**。所以生产固定用 `AcceptThreshold = 0`，判定与"值不值得抓"全部由程序自己算。
5. **PatMax 模板原点默认是 `(0,0)`＝图像左上角**，不是工件。判定 OK/NG 不受影响，但拿它驱动机械臂会整体偏移且全程无报错。程序在训练后与标定计算前强制核对原点，不通过不允许保存。
6. **N 点标定 API 返回的是反向变换**（像素 ← 毫米），要得到像素 → 毫米必须 `Invert`；反变换矩阵行列式为负说明 X/Y 配成了镜像，机械臂会往反方向走——程序直接拒绝保存，并给中文排查指引。
7. **取料点必须落在抓取工作范围内**（默认 X 120–280 / Y −80–80 mm）。宁可先"拒动"让人来调范围，也不要先撞一次；现场按工件实际可能出现的位置放大这四个数。
8. **生产运行时设备调试页整页互锁置灰**：传送带与机械臂各只有一份物理资源，两处并发下发命令会产生难复现的故障。要手动点动，先停生产。
9. **主循环跑在后台线程**，且逐格定义了异常策略：写库/存图失败只记备注不打断节拍、机械臂异常仍写库、取像连续 3 次失败才判故障、检测 2000ms 看门狗、急停走取消令牌 + 停带 + 锁存。改动流程时**不要**把某一步改成"失败就抛异常打断"——生产节拍不能被任何一步挂死。
10. **库是可选依赖**：连接串 3 秒超时，库不可达时结果先进 `pending_results.jsonl`，库恢复后自动补齐（每行带客户端 `uuid` + `UNIQUE KEY` + `INSERT IGNORE`，重试不产生重复行）。不要为了"保证写进去"把它改成阻塞式重试。
11. **`App.config` 不要加 DpiAwareness / `ApplicationConfigurationSection`**（见 §四）。高 DPI 要真正支持，是把 `MainForm` 与 5 个视图的 `AutoScaleMode` 改成 `Dpi`、基准改 `(96,96)` 后逐页复验，那是独立改动。
